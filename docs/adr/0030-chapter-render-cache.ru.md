# 0030. Кэш дерева главы и хром на нотифаерах

**English** | [Русский](0030-chapter-render-cache.md)

Status: принят (2026-10-18).

## Контекст

Экран чтения — один `State` (`_ReadingScreenState`, пять `part`-файлов).
Каждый `setState` пересобирает главу целиком: `TextSpan`/`WidgetSpan` и
распознаватели жестов создаются заново в `_buildChapter` при каждом
проходе. Динамическое состояние запечено в спаны — выбранный стих,
читаемый вслух стих и читаемое вслух *слово* (`_selectedVerse`,
`_ttsVerse`, `_ttsWord`); тик слова приходит несколько раз в секунду,
поэтому длинная глава в «Изучении» с подстрочником стоила полной
пересборки тысяч спанов на каждое произнесённое слово. Мусор
распознавателей собирался вручную (`_rotateTapRecognizers`); кэш
`_lineCache` покрывал только вторые строки (сравнение/подстрочник), а
его записи могли держать распознаватели, которые ротация уже успела
уничтожить.

От этого заблокированы три дорожки: 120 fps на длинных главах
(требование Alpha), мультипанельные рабочие места (ADR 0014 — панели
не должны перестраивать друг друга) и собственная текстовая система
(ADR 0021 — её тайпсеттеру нужна модель «текст = кэшируемая функция
состояния»).

Ключевое наблюдение: в каждый момент состояние выбранного/читаемого
стиха затрагивает один-два стиха. Всё остальное кэшируемо.

## Решение

1. **Кэш строк главы** (`ChapterLineCache`, `lib/reader/line_cache.dart`):
   построенные виджеты кэшируются по ключу — строки стихов `L:стих`,
   блоки абзацев `B:блок`, строки строчного сравнения `I:стих`, вторые
   строки `S:модуль:стих` и строки подстрочника `P:…` (как раньше).
   Peek-страницы листания — с префиксом `p|`. Кэш очищается при смене
   сигнатуры рендера (`_syncLineCache`: модуль, глава, вёрстка,
   настройки отображения, палитра, словарь, конверсии, режим
   подстрочника) и при перечитке записей пользователя
   (`_loadVerseEntries`).
2. **Динамическое исключение**: строка *динамическая*, если содержит
   выбранный или читаемый вслух стих. Динамические строки строятся мимо
   кэша; их устаревшие записи удаляются, пока они активны. Стих,
   переставший быть активным, перестраивается один раз (чистая стилизация)
   и возвращается в кэш. В абзацном режиме *блок* динамический, если
   содержит активный стих; курсор спанов перестроенного блока засевается
   счётчиками активного стиха из предшествующих блоков (стих тянется
   через границу блоков в поэзии; смещения `_hlFrags` и слова TTS должны
   остаться непрерывными).
3. **Владение распознавателями**: распознаватели, созданные при сборке
   кэшируемой строки, принадлежат записи кэша и утилизируются при
   выселении, очистке по сигнатуре и закрытии экрана (с отсрочкой до
   конца кадра — виджет мог ещё участвовать в прошлом кадре). Некэшируемые
   построители сохраняют прежнюю покадровую ротацию. Заодно чинится
   скрытая ошибка старого `_lineCache`: записи вторых строк держали
   распознаватели, которые ротация уже уничтожила.
4. **Хром на нотифаерах**: видимость панелей, плавающее поле поиска и
   панель сносок переходят на `ValueNotifier` с локальными
   `ListenableBuilder`. Переключение хрома больше не пересобирает текст.
   Десктопная панель сносок получает контроллер скролла — поле состояния
   (раньше создавался в `build()` — сброс позиции и утечка при каждой
   пересборке).
5. **Маршрутизация тиков TTS**: тик слова обновляет только активную
   строку (нотифаер, который она слушает); тики стихов остаются на
   уровне экрана (дёшево после п. 1). Состояние плеера/медиа — свой
   колбэк.
6. **Список сравнения — панели, не настройки**: список модулей
   строчного сравнения, восстановленный из снимка позиции, идёт в поле
   экрана (`_interleavedOverride`), а не в `Settings.interleavedModules` —
   навигация больше не пишет глобальную настройку на каждом шаге
   назад/вперёд.

## Последствия

- Стоимость `setState` всего экрана падает до хрома плюс одна-две свежие
  строки; тик слова перестраивает одну строку.
- Кэшированные строки переживают смену выделения/TTS; тапы и лонг-прессы
  кэшированных строк работают весь срок жизни записи.
- Кэширование ленты книги (`_bookBlocks`) отложено — лента пока
  перестраивается на каждый `setState` (продолжение в рамках этого ADR).
- Кэш держит виджеты, а не RenderObject — память единицы МБ на главе
  с подстрочником, освобождается при смене сигнатуры.
- Сеялка курсора динамических блоков повторяет правила счётчиков
  `_spanOf`; обе стороны меняются вместе.

## Дополнение 18.10.2026 — лента книги и замеры

1. **Лента книги кэшируется** (`_bookBlocks`, в тот же день): ключи
   `bk:<глава>:B:<блок>` (префикс `p|` для подгляда). Цвет номера стиха
   зависит от `_selectedVerse` без привязки к главе, поэтому блок с
   выбранным/читаемым стихом консервативно динамичен в **любой** главе
   ленты; сама подсветка TTS/выделений рисуется только в главе `_ch` —
   и только ей нужен засеянный курсор. `_bookBlocks` минует
   `_buildChapter`, поэтому теперь сам зовёт `_syncLineCache` — без
   этого кэш ленты не инвалидировался бы при смене настроек.
2. **Диагностика и выключатель** (`line_cache.dart`): счётчики
   попаданий/промахов (экземплярные и статические
   `ChapterLineCache.totalHits/totalMisses`) и компиляционный флаг
   `STUDYBIBLE_NO_RENDER_CACHE` — с ним каждая строка идёт динамическим
   путём, воспроизводя поведение до ADR 0030 для честных замеров.
3. **Бенч** (`test/render_bench_test.dart`): настоящий `ReadingScreen`
   на engbsb Пс 119 (176 стихов, «Изучение»), холодная сборка + 20
   горячих пересборок (нотификации настроек) + дым ленты книги.
   Аппаратное время в тестовой среде (без растеризации) — осмысленны
   только отношения ON/OFF:

   | Сценарий (Пс 119, «Изучение») | кэш вкл | кэш выкл | разница |
   |---|---|---|---|
   | холодная сборка главы | 117 мс | 118 мс | штрафа первой сборки нет |
   | горячая пересборка экрана, средняя (глава) | 19,4 мс | 22,3 мс | ~12 % |
   | горячая пересборка экрана, средняя (лента книги) | 14,8 мс | 20,0 мс | ~26 % |
   | кэш после 20 горячих пересборок | 3 520 попаданий / 0 промахов | 0 / 0 | 100 % попаданий |

   На устройстве разрыв должен расти: построение виджетов и
   распознавателей конкурирует там с реальной растеризацией. Выигрыш
   тика слова в этих числах не виден напрямую: тик перестраивает одну
   обёрнутую строку (нотифаер), бенч же меряет пересборки уровня
   экрана — именно столько стоил каждый тик до изменения.
