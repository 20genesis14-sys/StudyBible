# 0022. Блоб-упаковка spans/tokens/alignment внутри .sb

[English](0022-packed-span-storage.md) | **Русский**

Статус: принято (10.10.2026).

## Контекст

Текстовый модуль заметно тяжелее источника: `eng-kjv2006` — 13 МБ USFM,
но 88 МБ `.sb`. Замер показал: вес не в тексте (`verses.text` — всего
~4 МБ), а в накладных на строку — ~649 тыс. `t`-спанов, ~350 тыс.
токенов, ~350 тыс. строк alignment. Каждая строка несёт ~10 колонок
ключей плюс B-tree первичного ключа; «конверт» стоит 40–60 байт на
строку — десятки мегабайт чистых накладных.

У всех трёх таблиц один паттерн доступа: читаются **целиком на
главу/стих** (рендер главы, карточка Стронга, подстрочник), никогда —
точечно по ключу строки. Это кандидаты на векторизацию: одна строка на
единицу (блок или стих) с компактным бинарным массивом.

Это **не** формат v2 (ADR 0018): файл остаётся SQLite,
`format_version` остаётся `"1"`, прочие таблицы построчные. Это
эволюция v1 в рамках правила «только необязательные добавления» — но
поскольку данные физически уходят из `spans`, читатель без поддержки
упаковки молча потерял бы Стронга/стили. Поэтому упаковка объявляется
**обязательной возможностью** (`meta.required="pack"`): старые
читатели отказывают явно, а не деградируют молча.

## Решение

Три новые необязательные таблицы хранят varint-упакованные данные:

- `span_pack(book_id, chapter, block, blob)` — все `t`-спаны блока в
  порядке `seq`. Запись: `seq`, `verse` (NULL = заголовочный/вводный
  текст), `start`,`len` (NULL у заголовочного текста), `style`,
  `attrs`, `text` (непусто только у заголовочного текста). Строки —
  через пул на блоб (style/attrs повторяются массово: `"w"`,
  `strong="…"`).
- `token_pack(book_id, chapter, verse, blob)` — токены стиха: `seq`,
  `surface`, `lemma`, `strong`, `morph`, `gloss`.
- `align_pack(book_id, chapter, verse, blob)` — тройки `token_seq →
  (block, span)`.

Кодировка блоба: LEB128-varint'ы, затем пул строк (число + строки с
длиной), затем записи с байтом флагов присутствия опциональных полей.
Формат заморожен в кодеке (`store::pack`); spec `05` документирует его
для сторонних.

Таблицы `spans`, `tokens`, `alignment` сохраняют схему (создаются
пустыми) — старые проверки колонок и инструменты работают; `f`/`x`/`v`
спаны и все прочие таблицы (`variants`, `readings`, `witnesses`,
`entries`, `marks`, `book_headers`) остаются построчными: их мало,
у них есть текстовые тела или нужен точечный доступ (`entries.norm`).

Чтение: `chapter()` сливает строки `spans` и записи `span_pack` по
блоку в порядке `seq`; `tokens()`/`alignment()` распаковывают блобы
стихов. Ветка читателя выбирается по наличию pack-таблиц; модули без
упаковки читаются без изменений.

`content_hash` считается по логическому потоку чтения, поэтому
одинаков у упакованной и неупакованной сборок одного источника.

## Последствия

- `eng-kjv2006.sb`: ~88 → ~50 МБ ожидается; `.sbz` 21,5 → ~14–16 МБ.
- Упакованный модуль не откроется старым читателем — он сообщит
  `UnsupportedFeature("pack")`. Новые читатели читают оба вида.
- SQL-прозрачность разметки Стронга теряется (разметка в блобах);
  текст `verses` остаётся обычным SQL. У CLI есть путь распаковки —
  публичный кодек `store::pack`.
- Инструменты, пишущие `f`/`x`-строки (`inject_xrefs`), не затронуты —
  эти спаны остаются построчными.
- ADR 0018 (v2) не меняется: блоб-кодек может позже стать
  сериализацией полезной нагрузки v2.

## Дополнение 2026-10-14 — ленивое чтение модуля: два отложенных варианта

Мотивация: `sqlite3_deserialize` держит весь распакованный модуль в
ОЗУ (~13 МБ у russyn, десятки МБ у тяжёлого модуля, умножаясь на число
открытых), а на вебе весь `.sbz` скачивается до первой главы. Обзор
сторонних проектов `mlin/sqlite_zstd_vfs` и `phiresky/sqlite-zstd`
подтвердил пространство идей; ни один не принят — первому нужен C++-VFS
на всех платформах (sqlite3.wasm расширения не грузит), второй
переписывает таблицы в view и дублирует наш pack-подход — но его схема
«словарь на чанк» заимствована.

Зафиксированы два дизайна как **равноценных кандидата; выбор отложен**
до начала работ по ленивому чтению (OPEN-QUESTIONS № 47):

- **Вариант A — блочный контейнер + общий словарь + страничный VFS.**
  Образ `.sb` режется на фреймы (~64 КБ), каждый жмётся zstd с общим
  обученным словарём (`dictID` в каждом фрейме; словарь — в заголовке
  файла). Индекс смещений фреймов даёт случайный доступ; собственный
  `sqlite3_vfs` (Rust / FS-слой sqlite3.wasm) распаковывает только
  фреймы под запрошенные страницы с ограниченным LRU-кэшем. ОЗУ ≈ 1–2
  МБ на модуль; на вебе те же фреймы тянутся по HTTP Range — глава
  это доля файла. Цена: новый контейнер, VFS на всех платформах,
  чуть худший коэффициент, чем у единого потока (словарь закрывает
  бо́льшую часть разрыва).
- **Вариант C — `text_pack`: сжатие текста стихов по главам внутри
  `.sb`.** `verses.text` уходит в `text_pack(book_id, chapter, blob)`
  — один zstd-блоб на главу с тем же общим словарём; спаны уже несут
  байтовые срезы `(verse,start,len)`, они индексируют расжатый текст
  главы, меняется только выборка текста стиха. Файл остаётся обычным
  `.sb`: обычный файловый I/O, VFS не нужен, страничный кэш ОС даёт
  ленивость бесплатно; ОЗУ = LRU-кэш расжатых глав (~2–4 МБ). Цена:
  читаемый файл растёт (~3,5–4,5 МБ у russyn — индексы и pack-блобы
  не жмутся), поэтому `.sbz` перестаёт окупаться как транспортная
  обёртка; на вебе файл качается целиком, пока не добавлено чтение по
  Range (эталон: `sql.js-httpvfs` от phiresky).

Общие решения в любом случае: словарь тренируется один раз на реальных
данных модулей (`zstd --train`), идентифицируется `dictID`, поставляется
в заголовке файла (самодостаточность) или внутри приложения; естественная
гранулярность блока — глава. `content_hash` не затрагивается — он
считается по логическому потоку чтения. Ни один вариант не меняет
принятую схему v1 и трек ADR 0018; оба дешевле v2 и могут стать его
запасным шагом.
